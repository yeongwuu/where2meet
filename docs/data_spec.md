## 3. 파일별 필드

### 3-1. `members.json`: 같이 갈 사람

팀 구성 규칙 (전 팀 같음)
- 팀: Assurance 1~8팀, Tax 1~3팀, Deals 1~3팀. 팀마다 8~9명
- 팀마다 파트너(임원) 1명, 상사(매니저·디렉터) 2명, 취향 미입력 1명
- 알레르기는 취향 입력한 사람의 약 16%, 채식·할랄은 약 8%. 술·분위기는 팀마다 성향이 조금씩 달라요
- 닉네임은 순우리말 두 글자, 전원 겹치지 않음
- 처음 12명(`p01`~`p12`)은 처음 데이터 그대로예요. 하늘(체험 계정)은 Assurance 3팀이고, 하랑·한결·누리만 2·4·5팀으로 소속을 옮겼어요

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | `p01` 형식 |
| `nickname` | string | 화면에 보이는 이름. 실명 대신 닉네임 |
| `team` | string | 팀 이름. ② 팀 그룹으로 묶을 때 써요 |
| `rank` | `rank_*` | 직급. 상사·임원 배지를 정해요 (아래 3-5) |
| `is_member` | boolean | `false`면 아직 취향을 입력하지 않은 사람. 화면에서는 "취향 모름"/"미입력" |
| `allergies` | `allergy_*`[] | 못 먹는 것 (알레르기) |
| `diet` | `diet_*`[] | 못 먹는 것 (식단) |
| `likes` | `food_*`[] | 좋아하는 음식. ①에서는 더 이상 묻지 않아요 (아래 3-1-1). ③·④가 바뀔 때까지 샘플 값을 남겨 둬요 |
| `dislikes` | `food_*`[] | 별로인 음식 (`likes`와 겹치지 않음). ①에서는 더 이상 묻지 않아요 (아래 3-1-1). 샘플은 0~2개, 채식은 고기구이 · 생선·갑각류·조개 알레르기는 해산물을 먼저 넣었어요. 미입력이면 `[]` |
| `not_today` | `food_*`[] | 오늘은 먹고 싶지 않은 음식. 0~2개 (아래 3-1-1). 미입력이면 `[]` |
| `drink` | `drink_*` \| null | 술. 미입력이면 `null` |
| `mood` | `mood_*` \| null | 분위기. 미입력이면 `null` |

#### 3-1-1. 오늘은 먹고 싶지 않은 음식 `not_today`
①의 "좋아하는 음식"·"별로인 음식" 입력을 이 한 칸으로 줄였어요. 여러 음식을 다 고르게 하는 대신, 오늘 피하고 싶은 것만 짧게 받아요.

- 선택지: 2-1의 `food_*` 8개. 작은 칩(`chips-sm`)으로 보여 줘요
- 개수: 0~2개. 0개도 괜찮아요("없으면 고르지 않아도 돼요"). 3개째를 누르면 고르지 않고 "2개까지 고를 수 있어요. 하나를 빼고 다시 골라 주세요"를 안내해요
- 상한은 `src/js/labels.js`의 `NOT_TODAY_MAX`(2). 바꾸면 이 문서도 같이 고쳐요
- 못 먹는 것(알레르기·식단)과 달리 반드시 지키는 조건이 아니에요. 취향 입력한 사람만 집계하고, 누가 골랐는지는 화면에 드러내지 않아요
- 저장: ① 내 프로필(`w2m.profile`)에 `not_today`로 저장해요. 예전에 저장한 `likes`·`dislikes`는 지우지 않고 그대로 둬요
- 샘플: 취향 입력한 회원마다 0~2개 (0개 33명 · 1개 50명 · 2개 23명). `dislikes`에 있는 음식을 먼저 넣었어요. 미입력 회원은 `[]`
- ④ 점수(4-3)에 반영했어요 (안 당기는 사람 비율 × 30 감점). ③ 취향 종합에는 따로 보여 주지 않아요

### 3-3. `guests.json`: 비회원
② 비회원 목록, ⑤ 비회원 메모 카드에서 써요. ②에서는 평소에 고른 비회원만 보이고, 검색(호칭·회사·부서)으로 찾아서 더해요. g01~g03(목업의 3명)만 메모·취향 샘플이 있고, 나머지는 비어 있어요.

②의 "+ 비회원 추가"로 만든 비회원은 파일이 아니라 브라우저(`w2m.guests`)에 저장돼요. id는 `gm` + 숫자, `mine: true`가 붙어요. 관계가 거래처면 `group`은 고객사, 나머지는 사내예요.

구성
- `g01`~`g03`: 목업의 3명 (재무본부 상무님, A사 재무팀장님, 감사본부 파트너님)
- 사내 백오피스 24명: 회계팀·재무팀·인사팀·교육팀·총무팀·IT지원팀·법무팀·홍보팀 × 팀장님·과장님·대리님
- 고객사 77명: A사~Z사 × CFO님·재무팀장님·회계부장님 (A사 재무팀장님은 `g02`)

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | `g01` 형식 |
| `title` | string | 호칭 (예: "A사 CFO님"). 실명 쓰지 않음 |
| `org` | string | 회사 또는 부서 (예: "A사", "인사팀") |
| `group` | `사내` \| `고객사` | 구분 |
| `relation` | string | 관계 배지: `임원` / `상사` / `거래처` / `사내` (백오피스 직원) |
| `allergies` | `allergy_*`[] | 아는 범위의 못 먹는 것 |
| `diet` | `diet_*`[] | |
| `likes` | `food_*`[] | 좋아함. ⑤ 메모 카드·수정에서는 더 이상 보여 주지 않아요 (예전 값은 그대로 둬요) |
| `dislikes` | `food_*`[] | 별로. ⑤에서 보여 주지 않아요 (예전 값은 그대로 둬요) |
| `needs` | string[] | 꼭 필요 (예: "룸", "주차") |
| `memo` | string | 메모 본문. 나만 보기 |
| `history` | `{date, text, from_review_id}`[] | 기록 줄. 후기를 올리면 여기에 추가돼요 |

### 3-4. `reviews.json`: 후기 (초안)
| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | `v01` 형식 |
| `restaurant_id` | string | `restaurants.json`의 `id` |
| `meeting_title` | string | 모임명 |
| `date` | string | `YYYY-MM-DD` |
| `purpose` | string | 목적 (예: 팀 회식) |
| `with` | string | 동석 (예: 임원 동석) |
| `headcount` | number | 인원 |
| `rating` | number | 별점 1~5 |
| `chips` | string[] | 칩 후기 (예: "룸이 조용해요") |
| `comment` | string | 한마디 |
| `guest_notes` | `{guest_id, text}`[] | "OO님에 대해 알게 된 것" → 해당 비회원 `history`에 추가 |

⑤에서 올린 후기는 파일이 아니라 브라우저(`w2m.reviews`)에 저장돼요. id는 `vm` + 숫자이고, 어느 확정에 대한 후기인지 알 수 있게 `confirmed_at`(모임 `confirmed.confirmedAt`과 같은 값)이 붙어요. 이 값이 같은 후기가 있으면 "1건 남음" 카드 대신 "후기를 올렸어요" 한 줄을 보여 줘요.

후기 카드의 "다음에 하기"를 누르면 그 모임의 `confirmedAt`을 `w2m.reviewLater`(목록)에 넣어요. 홈은 이 목록에 있는 후기를 다시 알리지 않고, ⑤에서는 카드가 "다음에 쓰기로 했어요" 한 줄과 [지금 쓰기] 버튼으로 바뀌어요. [지금 쓰기]를 누르면 목록에서 빼고 후기 카드를 다시 보여 줘요 (홈 알림도 다시 떠요).

⑤에서 고친 비회원 메모도 파일은 그대로 두고 `w2m.guestMemos`에 `{ 비회원 id: 바뀐 필드 }`로 덮어써요. 후기의 `guest_notes`는 그 비회원 `history`에 `{date: 올린 날, text, from_review_id: 후기 id}`로 쌓이고, 메모 카드에는 마지막 기록 한 줄만 보여 주고, 이전 기록은 "기록 n개 더 보기"를 누르면 최신순으로 펼쳐져요.

### 3-5. 상사·임원 배지
| 대상 | 기준 |
|---|---|
| 회원 | `rank_partner` → 임원 · `rank_manager`, `rank_director` → 상사 · 나머지는 배지 없음 |
| 비회원 | `relation` 값을 그대로 (`임원` / `상사` / `거래처`) |
| 나 | 배지 없음, 인원 요약의 임원·상사 수에서도 빠져요 |

### 3-6. 모임 (브라우저에 저장, 파일 없음)
② 모임 만들기에서 만들어 ③ 이후 화면으로 넘겨요. 저장 키는 `w2m.meeting`이에요. (내 프로필은 `w2m.profile`, ②에서 내가 추가한 비회원은 `w2m.guests`)

②에서 취향 미입력 배지를 눌러 입력을 부탁하면 `w2m.requests`에 `{ 회원 id: 부탁한 시각 }`으로 저장되고 배지가 "요청함"으로 바뀌어요. 지금은 서버가 없어서 실제 알림은 가지 않아요.

| 필드 | 타입 | 설명 |
|---|---|---|
| `people` | string[] | 고른 사람 id. 회원 `p*`, 비회원 `g*`, 나 포함 |
| `purpose` | `purpose_team` \| `purpose_farewell` \| `purpose_client` | 팀 회식 / 환영·송별 / 접대 |
| `budget` | [number, number] | 1인 예산 [최소, 최대] 원. 최대 `100000`은 "10만원 이상" |
| `day` | `day_today` \| `day_tomorrow` \| `day_pick` | 오늘 / 내일 / 날짜 선택 |
| `date` | string | `day_pick`일 때 `YYYY-MM-DD` |
| `time` | string | 시간 `HH:MM`. 점심 11:30~13:00, 저녁 17:00~20:00 중에서 골라요 (기본 18:30) |
| `team` | string | 소속 팀. 이 팀 사람이 처음에 모두 체크돼요 |
| `place` | `place_*` | 회사 / 신용산역 / 용산역 / 삼각지역 |
| `walk` | `walk_5` \| `walk_10` \| `walk_15` | 도보 시간 |
| `apply` | `{character, food, drink}` (boolean) | ③ 스위치로 추천 반영 여부. 없으면 모두 `true`. 끈 항목은 ④ 점수에서 빼요 |
| `confirmed` | `{restaurant_id, name, confirmedAt}` | ④에서 "이 식당으로 확정"을 누르면 저장돼요. 없으면 아직 확정 전 |
| `updatedAt` | string | 마지막 수정 시각 |

## 4. 추천 로직
②에서 고른 사람과 모임 정보 → ③ 취향 종합 → ④ 추천 3곳 순서로 계산해요.

### 4-1. 취향 종합 (③)
- **취향 입력한 사람**: `is_member: true`인 사람만 집계해요. 나머지는 "취향 모름 n명"으로 따로 보여 줘요.
- **반드시 피할 것**: 고른 사람 전체의 `allergies`, `diet`를 합쳐요. 이름 없이 "갑각류 1명"처럼 인원만 보여 줘요. 스위치로 끌 수 없어요.
- **다 같이 좋아하는 음식**: `food_*`마다 `likes`에 들어 있는 사람 수를 세어 많은 순으로 막대를 그려요.
- **술·분위기**: `drink`, `mood` 비율을 막대로 보여 주고, 가장 많은 값으로 결론 한 줄을 만들어요. (예: "반주 정도의 식사 중심", "조용한 곳에서 반주 정도의 식사 중심")
  - 술: `drink_none` → 술 없이 식사 중심 · `drink_light` → 반주 정도의 식사 중심 · `drink_enjoy` → 술자리 중심. 같은 수면 덜 마시는 쪽
  - 분위기: `mood_quiet`·`mood_lively`가 가장 많으면 "조용한 곳에서 / 활기찬 곳에서"를 앞에 붙여요. `mood_any`가 가장 많거나 같은 수가 있으면 붙이지 않아요 (중립)

### 4-2. 조건 거르기 (꼭 지켜야 하는 것)
아래 중 하나라도 어기면 추천에서 빼요. 못 먹는 것과 갈 수 없는 곳, 예산을 크게 넘는 곳만 걸러요. 나머지 예산·도보는 점수(4-3)로 반영해요.
1. 식당 `allergens`와 고른 사람들의 `allergies`가 하나라도 겹침
2. 고른 사람 중 `diet`가 있는데 식당 `diet_ok`에 그 식단이 없음
3. `capacity` < 인원 (자리가 모자라면 갈 수 없어요)
4. `price_per_person`이 ②의 예산 최대보다 1.5만원 이상 비쌈 (최대가 "10만원 이상"이면 거르지 않아요)
5. 모임 날짜의 요일이 `closed`에 있음
6. 모임 시간이 `hours` 밖임

남은 식당 수를 ④ "조건을 지키는 곳 n곳"에 보여 줘요.

### 4-3. 점수 (순위 정하기)
남은 식당마다 점수를 매겨 높은 순으로 3곳을 보여 줘요. ③에서 스위치를 끈 항목은 점수에서 빼요.

예산·도보·술·분위기·룸 각 최대 20점, 합계 최대 100점이에요. 예산은 범위를 벗어나면 −20점까지 내려가고, 오늘 안 당기는 음식은 최대 30점을 깎아요. (점수 범위 −50 ~ 100)

| 항목 | 계산 | 점수 | ③ 스위치 | 화면 근거 |
|---|---|---|---|---|
| 예산 | 1인 금액이 ②의 예산 범위 안이면 +20. 범위 밖으로 벗어난 5천원마다 −10 (5천원 → +10, 1만원 → 0, 1.5만원 → −10, 2만원 이상 → −20). 최대보다 1.5만원 이상 비싼 곳은 4-2에서 걸러져요. 최대가 "10만원 이상"이면 위쪽은 제한 없음 | −20 ~ 20 | 없음 (늘 반영) | ⚠ "예산보다 1인 1만원 비싸요" / "예산보다 1인 5천원 저렴해요", 기준 체크의 예산 줄 ⚠ |
| 도보 | ②의 "어디서"가 회사일 때 `walk_min`이 도보 시간 안이면 만점. 넘은 1분마다 −4 (최저 0). 역에서 모이면 데이터가 없어서 모두 만점 | 0 ~ 20 | 없음 (늘 반영) | ⚠ "회사에서 도보 13분이라 3분 더 걸려요", 기준 체크의 도보 줄 ⚠ |
| 술 | 결론(4-1)과 같으면 20, 한 단계 차이면 10, 두 단계 차이(식사 중심 ↔ 술자리 중심)면 0 | 0 / 10 / 20 | 술·분위기 | ✓ "반주 정도에 맞아요" / ⚠ "식사 중심이라 술자리로는 아쉬울 수 있어요" |
| 분위기 | 결론과 같으면 20, 결론이나 식당이 `mood_any`면 10, 정반대면 0 | 0 / 10 / 20 | 술·분위기 | ✓ "조용해서 대화하기 좋아요" / ⚠ "활기찬 곳이라 대화가 어려울 수 있어요" |
| 룸·자리 | 남는 자리(`capacity` − 인원)가 3보다 많으면 20, 3 이하면 10. 임원·상사 동석이거나 접대(거래처 포함)인데 `private_room: false`면 −10 (최저 0) | 0 ~ 20 | 모임 성격 (룸 부분만) | ✓ "룸 16인 · 임원·상사 모시기 좋아요" / ⚠ "룸이 없어요", "최대 12인이라 인원이 늘면 어려워요" |
| 오늘 안 당기는 음식 | 식당 `food` 중 하나라도 `not_today`(3-1-1)에 있는 사람 수 ÷ 취향 입력한 사람 수 × 30 만큼 감점 | 0 ~ −30 | 없음 (늘 반영) | 박스 "취향 입력한 8명 중 7명이 오늘 괜찮은 음식" / ⚠ "1명이 오늘은 한식·찌개가 안 당긴대요" (누가 골랐는지는 보여 주지 않아요) |

- 점수가 같으면 1인 금액이 낮은 곳이 앞이에요. 금액도 같으면 `restaurants.json`에 먼저 적힌 곳(id가 작은 곳)이 앞이에요.
- 1·2위가 동점이면 AI 요약 박스에 "산채정과 초록쌈 정식은 똑같이 잘 맞아요. 1인 금액이 낮은 곳을 먼저 보여 드려요."처럼 알려 줘요. 순서와 1순위 강조는 그대로예요.
- ③에서 끈 스위치의 항목은 점수와 ✓/⚠ 근거에서 모두 빠져요. 못 먹는 것(4-2)은 끌 수 없어요.
- 취향 모름(`is_member: false`)과 비회원은 오늘 안 당기는 음식·술·분위기 계산에서 빠지고, 못 먹는 것과 인원만 반영돼요.
- `likes`·`dislikes`는 ④ 점수에서 더 이상 쓰지 않아요. (③ 취향 종합은 아직 씀, 5장)
- ③ 취향 종합의 "다 같이 좋아하는 음식" 카드와 음식 스위치는 없앴어요. ③에 남은 스위치는 모임 성격·술·분위기 두 개예요.
- 코드: `src/js/result.js`의 `WEIGHT`, `BUDGET_STEP`, `BUDGET_STEP_POINTS`, `BUDGET_FLOOR`, `BUDGET_OVER_LIMIT`, `WALK_MINUTE_POINTS`. 바꾸면 이 표도 같이 고쳐요.

### 4-4. 근거 문장 (④ 카드)
같은 내용이 두 번 나오지 않게 나눠서 보여 줘요.

- **카드 위 추천 이유** (접힌 상태에서도 보임): 술·분위기·오늘 안 당기는 음식만 짧게. ✓ "반주 정도에 맞아요" · "조용해서 대화하기 좋아요" / ⚠ "1명이 오늘은 한식·찌개가 안 당긴대요". 해당하는 게 없으면 목록을 그리지 않아요
- **펼친 카드 순서**: 식당 정보 → "○○ 기준 체크" → 후기 → [공지 문구 복사 · 이 식당으로 확정]
- **식당 정보**: 영업시간(`hours`, 휴무가 없으면 "매일"을 붙이고 자정을 넘기면 "다음 날", `break_time`·`last_order`가 있으면 아래 줄에) · 휴무(`closed`, 없으면 "연중무휴") · 주차(`parking`) · 참고(`notes`), 맨 아래 정보 확인일. 주소·전화번호는 보여 주지 않아요
- **기준 체크** (✓ 지킴 / ⚠ 확인 필요): 알레르기 · 식단(채식·할랄 대응, 오른쪽 "예약 때 미리 요청") · 룸·인원(룸이 필요한 모임인데 룸이 없거나, 남는 자리가 3 이하면 ⚠) · 예산(범위 밖이면 ⚠) · 도보(회사에서 모일 때, 시간을 넘으면 ⚠)
- 취향 모름 인원과 "알레르기·식단 정보는 방문 전 식당에 한 번 더 확인해 주세요"는 카드마다 반복하지 않고 AI 요약 박스와 화면 맨 아래에 한 번만 보여 줘요

## 5. 아직 정하지 않은 것
- `not_today`는 ④ 점수(4-3)에 반영했고, ③의 "다 같이 좋아하는 음식"은 없앴어요. 이제 회원(`members.json`)의 `likes`·`dislikes`는 어느 화면에서도 쓰지 않아서 정리해도 돼요. 비회원(`guests.json`)의 `likes`·`dislikes`는 ⑤ 비회원 메모에서 계속 써요.
- 영업시간·휴무·주차·정보 확인일과 회사 기준 도보 시간(`walk_min`)은 3-2에 추가했어요 (시연용 가상 값).
- 역(신용산역·용산역·삼각지역) 기준 도보 시간은 아직 없어요. ②에서 역을 고르면 도보 시간으로 거르지 않고, 카드에는 회사 기준 시간만 보여 줘요. 필요하면 `walk_min`을 `{place_office: 9, place_sinyongsan: 4, …}` 같은 객체로 바꾸는 걸 제안해요.
- 오래된 정보(`info_checked`가 오래됨)를 ⚠로 표시할 기준은 아직 정하지 않았어요.
